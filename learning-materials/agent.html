1

标题与一句话定义

Agent（智能体）就是：让大模型在一个循环里自己决定下一步用什么工具、做什么动作，并依据环境的真实反馈不断调整，直到把任务做完。

换个大白话说：普通的 LLM 调用像「一问一答」的答题机器，你问一句它答一句；而 Agent 像一个被交代了目标的下属——它会自己拆任务、查资料、动手做、发现错了再改，中途遇到拿不准的才回来问你。

Anthropic 在《Building effective agents》中给出的收敛定义非常精炼：LLMs autonomously using tools in a loop（大模型自主地在循环中调用工具）。

2

核心机制与组成

2.1 四个必备零件

🧠 推理引擎（LLM）

负责理解目标、拆解步骤、决定调用哪个工具、判断任务是否完成。它是「大脑」。

🛠 工具集（Tools）

负责真正动手：读文件、跑命令、调 API、搜网页。它是「手」。工具文档写得清不清楚，直接决定 Agent 好不好用。

📚 记忆（Memory）

短期记忆放在上下文窗口里；长期记忆落在文件系统、数据库或向量库中，跨会话保留。

🔁 编排循环（Orchestration）

把上面三者串起来的骨架，驱动「思考 → 行动 → 观察」不断迭代。

2.2 主循环：收集上下文 → 行动 → 验证 → 重复

        ┌──────────────────────────────────────────┐
        │                                          │
        ▼                                          │
  ① 收集上下文  ──▶  ② 采取行动  ──▶  ③ 验证结果 ──┘
  (gather context)   (take action)   (verify work)
   读文件 / grep        调工具 / 改文件    跑测试 / 看报错
                                          │
                                     不通过则回到 ①

关键在于第 ③ 步：Agent 必须能从环境拿到真实反馈（ground truth）——比如工具返回值、代码执行结果、测试通过与否。没有反馈的循环是自说自话，有了反馈才能自我纠错。

2.3 两类「智能体系统」：Workflow 与 Agent

维度Workflow（工作流）Agent（智能体）
控制流由开发者用代码预先写死由模型在运行时动态决定
步数固定、可预测不固定，按需展开
优势稳定、一致、成本低灵活、能应对开放问题
典型模式Prompt chaining、路由、并行、评估-优化自主多轮工具调用

实践建议：先找最简单的方案，只有当复杂度确实带来效果提升时才往上加。Workflow 能解决的，别硬上 Agent。

具体应用场景

案例：编码 Agent 修复一个真实的 Issue

这是 Agent 目前最成熟、也最容易验证的落地场景（SWE-bench 类任务）。假设你给它的指令是「修复 #142：导出 CSV 时中文乱码」：

  1. 1
    收集上下文：用 grep 搜索 export 相关代码，读取命中的两个文件，而不是把整个仓库塞进上下文。
  2. 2
    采取行动：定位到 toCSV() 缺少 BOM 头，编辑文件补上 \ufeff。
  3. 3
    验证结果：运行单测与导出脚本，用命令行检查输出编码。测试仍红 → 读报错 → 回到第 1 步。
  4. 4
    收尾：测试通过，提交改动并汇报。遇到「要不要改公共 API」这类高风险决策时停下来问人。

为什么这个场景适合 Agent？因为它同时满足四个条件：任务开放（改法不唯一）、有明确成功标准（测试通过）、有反馈回路（报错即信号）、可插入人工审核（关键改动先确认）。

易混淆问题与使用边界

▶ Agent 和 Chatbot（聊天机器人）有什么区别？
Chatbot 的核心是「对话」——它输出文本，控制权在用户手里，你说一句它回一句。Agent 的核心是「交付结果」——它能调用工具改变外部世界的状态（写文件、发请求、改数据库），并且下一步做什么由模型自己决定。一个只会陪你聊「怎么修 bug」的是 Chatbot；真的把代码改了并跑通测试的是 Agent。
▶ Agent 和 Workflow 的边界到底在哪？
一个很好用的判据：控制流在谁手里。如果应用程序的执行路径由你的代码写死（先 A 再 B 再 C），那只是 Workflow；如果 LLM 能改变应用的控制流——决定要不要调 A、调几次、失败了换 D——那才是 Agent。LangChain 创始人 Harrison Chase 的表述是：“If the LLM can change your application’s control flow, it’s an agent.”
▶ Multi-Agent、Subagent 和 Agent 是一回事吗？
不是。Subagent（子智能体）是架构手段，不是 Agent 的同义词。它的价值主要有两点：一是并行提速，二是隔离上下文——子任务在独立的上下文窗口里折腾，只把结论回传给主 Agent，避免大量无关中间结果污染主上下文。多智能体只是「用多个 Agent 协作」的一种组织方式。
▶ 局限性：什么时候不该用 Agent？
  • 步骤可预测的任务：能写死流程就用 Workflow，Agent 只会增加不确定性和成本。
  • 成本与延迟敏感：自主意味着多轮调用，token 消耗和耗时都会成倍上升。
  • 错误会累积：一个小失误可能在后续步骤中被放大，所以要在沙箱里充分测试并加护栏。
  • 高风险不可逆操作：删除数据、强制推送、对外发消息等，必须留人工确认环节。
5

自测问题

Q1 你的团队做了一条规定：所有金额计算必须由代码完成，不许让模型「心算」。这是 Agent 设计中的什么考量？
参考答案：这是把确定性工作从模型手里剥离、交给工具的设计原则。LLM 负责推理与编排（决定算什么、怎么算），而具体计算交给可执行代码，这样既保证结果的准确与可复现，也避免 token 生成带来的误差和成本。同时也属于护栏（guardrails）设计——对不可出错的环节用确定性手段兜底。
Q2 一个系统里 LLM 会调用工具，但调用顺序被硬编码为「先查库 → 再调 API → 最后写文件」，永不变动。它是 Agent 吗？为什么？
参考答案：严格来说不是，它是 Workflow。判据是控制流的归属：这里每一步做什么、做几次都由代码预先固定，LLM 只在单步内做生成任务，无法改变应用的控制流。只有当模型能自主决定「要不要调、调哪个、失败了怎么办」时，才构成 Agent。这也提醒我们：很多号称 Agent 的产品其实只是 Workflow，选型时不必盲目追新。
