1

标题与一句话定义

上下文（Context）就是：模型在某一次请求里能看到的全部信息（所有 token）；而「上下文工程」就是在整个推理过程中，持续维护一个「最小且高信号」的 token 集合。

它不是「聊天记录」的别名。系统提示、工具定义、工具返回结果、历史消息、附件、技能、模型的思考块——只要进了这次请求，统统算上下文。你为输入 token 付费，也为输出 token 付费，而且窗口一旦塞满，请求直接失败。

所以目标从来不是「把所有东西都塞进去」，而是把对的东西塞进去。

2

核心机制与组成

2.1 上下文由什么构成

系统提示

角色、规则、输出格式等常驻指令。

消息历史

本轮之前的多轮对话内容。

工具定义

可用工具的名称、参数与说明，本身就占 token。

工具结果

长任务中最主要的膨胀来源，常被低估。

附件与技能

上传的文件、被加载的 Skill 内容。

思考块

模型的推理过程，同样计入上下文。

2.2 为什么要管理：注意力预算与上下文腐烂

Context Rot（上下文腐烂）

随着上下文 token 数增加，模型准确回忆其中信息的能力会单调下降。所有模型都逃不掉，区别只是下降的斜率。这是渐进式退化，不是硬悬崖——你不会看到「超过 N token 突然崩」，只会发现它越来越容易忽略细节。相关研究见《Lost in the Middle》：放在长上下文中间位置的信息，被模型有效利用的概率显著低于开头和结尾。

因此每新增一个 token 都在消耗模型有限的注意力预算。上下文应被视为边际收益递减的稀缺资源。

2.3 四种管理模式

模式做法解决什么
即时上下文
Just-in-time		 不预先全量加载，只保留轻量标识（文件路径、查询、链接），需要时用工具动态拉取。 窗口占用（设计层面的选择）
压缩
Compaction		 对话过长时，把历史轮次自动摘要成单个块，替换原文。 长会话撑爆窗口
提示缓存
Prompt caching		 把系统提示、工具定义等稳定部分标记缓存，跨调用复用。 成本与延迟
记忆工具
Memory tool		 把偏好、结论、进度写入外部记忆目录，跨会话存活。 无状态性（换会话即失忆）

生产环境通常是四种叠加使用：缓存稳定部分降成本、即时加载按需取数、压缩救长会话、记忆跨会话续接。

2.4 系统提示的「正确高度」

❌ 太具体：硬编码一长串 if-else 逻辑 → 脆弱、难维护
❌ 太模糊：只给「你要专业一点」      → 模型没有可执行的信号
✅ 正确高度：足够具体地约束行为，又留出让模型发挥的启发式空间

实践路径：先用最强模型试最小提示，观察失败模式，再逐条增量补充指令和少量典型示例。注意「最小」不等于「最短」，而是「刚好能完整描述期望行为」。

3

具体应用场景

案例：合规审查 Agent 与「即时上下文」

设想一个建筑合规审查 Agent，需要依据当地建筑规范判断方案是否合规。整本规范几十万字，直接塞进系统提示？窗口瞬间爆掉，且大部分条款跟当前问题无关。

✗
错误做法：把整本规范预加载进上下文。结果：成本高、注意力被稀释、模型反而更容易漏掉关键条款。
✓
正确做法：提供一个 lookup_building_code(section_id) 工具。Agent 判断当前需要查「消防通道宽度」，就按需把那一条拉进上下文；判断下一条时再拉下一条。

本质：这模仿的正是人类认知——我们不背下整座图书馆，而是靠目录、索引、书签在需要时精准取用。文件系统、收件箱、收藏夹，都是人类的「外部上下文管理系统」。

4

易混淆问题与使用边界

▶ 上下文（Context）和提示词（Prompt）是一回事吗？
不是。提示词通常指你写的那段指令文本；上下文是本次请求进入模型的全部 token，提示词只是其中一部分。相应地，提示工程关注「怎么写好一段提示」，上下文工程关注「在整个推理过程里，如何持续维护最优的信息集合」——后者覆盖系统提示、工具、MCP、外部数据、消息历史等所有来源，是一个动态、跨轮次的课题。
▶ 上下文窗口（Context Window）和记忆（Memory）有什么区别？
上下文窗口是易失的、单次的、有上限的——请求结束就没了，且塞满即失败。记忆是持久的、跨会话的、外部存储的——落在文件系统、数据库或向量库里，需要时再被读取「注入」上下文。二者的关系是：记忆是原材料仓库，上下文是当下的工作台。把长期信息留在仓库里、只在需要时搬上工作台，正是上下文工程的核心思路。
▶ 上下文工程和 RAG 是什么关系？
RAG（检索增强生成）是上下文工程的一种手段，不是同义词。RAG 通常指「推理前用向量检索预先取回相关内容」；而即时上下文策略则让 Agent 在运行时用工具动态加载（如 grep、SQL 查询、文件读取）。趋势是从「全部预先检索」转向「预检索 + 即时加载」混合：前者快，后者准且省。
▶ 局限性：窗口越大就越好吗？
  • 不等于更好。上下文腐烂依然存在，长上下文只是延缓问题，不能消除问题。精心裁剪上下文比单纯追求大窗口更有效。
  • 成本与延迟线性上升。每轮请求都要为全部输入 token 付费。
  • 工具集膨胀是隐形杀手。定义了几十个功能重叠的工具，光是工具定义就吃掉大量窗口，还会让模型选错工具。判据：如果人类工程师都说不清该用哪个，就别指望模型能选对。
  • 压缩会丢信息。摘要必然有损，关键信息应提前落盘到记忆或文件系统，而不是指望压缩保住它。
5

自测问题

Q1 模型有 100 万 token 的窗口，是不是就可以把所有资料一股脑丢进去了？请指出至少两个反对理由。
参考答案：
  1. 上下文腐烂：token 越多，模型准确召回其中信息的能力越低，位于中间的内容尤其容易被忽略（Lost in the Middle）。性能是梯度下降而非断崖，所以「塞得下」不等于「用得好」。
  2. 注意力预算：每个 token 都在争夺模型有限的注意力，无关信息会稀释关键信号，反而降低表现。
  3. 成本与延迟：每轮请求都为全部输入付费，长窗口会显著推高开销和响应时间。
  4. 正确做法：以「最小高信号 token 集合」为目标，用即时加载、压缩、缓存、记忆四种手段按需供给。
Q2 你的 Agent 跑了 200 轮后开始「忘记」最初的需求。有哪些手段可以缓解？它们解决的是同一类问题吗？
参考答案：可用四类手段，且针对不同失效模式，不应互相替代：
  • 压缩（Compaction）：把早期轮次摘要成块，解决窗口放不下的问题，但有损。
  • 记忆工具（Memory）：把目标、决策、进度写入外部记忆目录，解决跨会话 / 长任务的持久性问题——这才是「忘记最初需求」的正解，因为关键信息应当在压缩前就落盘。
  • 子智能体（Subagent）：把探索性子任务放进独立上下文窗口，只回传结论，避免无关中间结果污染主上下文。
  • 提示缓存：稳定前缀复用，只降成本，不解决遗忘。

实践要点：先落盘关键状态 → 再压缩 → 必要时拆分上下文。
