1

标题与一句话定义

Skill（技能）就是：一个装着 SKILL.md 的文件夹，把某领域的流程知识、脚本和资源打包起来，让 Agent 在需要时自己发现、按需加载。

打个比方：给 Agent 做 Skill，就像给新员工准备一份入职指南。你不必为每个用例重新造一个专用 Agent，只要把「这件事该怎么干」沉淀成一个可复用的文件夹，通用 Agent 就能秒变领域专家。

本页本身就是实例产物——它由本仓库的项目级 Skill .workbuddy/skills/concept-generator 生成。

核心机制与组成

2.1 一个 Skill 长什么样

my-skill/
├── SKILL.md          # 必需：YAML frontmatter + 正文指令
├── reference.md      # 可选：详细参考，按需读取
├── forms.md          # 可选：特定场景才用到的说明
└── scripts/
    └── validate.py   # 可选：可执行脚本，只回传输出

SKILL.md 必须以 YAML frontmatter 开头，包含两个必需字段：name 和 description。 

---
name: pdf-processing
description: 从 PDF 提取文本和表格、填写表单、合并文档。
  当处理 PDF 文件、表单或文档抽取任务时使用。
---

2.2 核心设计原则：渐进式披露（Progressive Disclosure）

这是 Skill 能兼顾「能力丰富」与「上下文节俭」的关键。分三层按需加载：

L1
元数据层 · 始终加载

启动时，所有已安装 Skill 的 name + description 被预加载进系统提示。每个约 100 token。它只告诉模型「有这么个技能、什么时候该用」，不占用实质内容空间。

成本 ≈ 100 tokens / 个
L2
指令层 · 触发时加载

模型判断某个 Skill 与当前任务相关时，才用工具（如读文件）把完整的 SKILL.md 正文读进上下文。

成本 < 5k tokens，建议控制在此范围内
L3+
资源层 · 按需再加载

附加的参考文件、模板、脚本。模型需要时才读；脚本执行时只有输出结果进上下文，代码本身不进。因此 Skill 可捆绑的内容量实际上没有上限。

成本 ≈ 无上限内容，0 上下文惩罚

类比：一本组织良好的手册——先看目录（L1），再翻到相关章节（L2），最后才查附录细节（L3）。你不会因为手册厚就把它整本背下来。

2.3 脚本：把确定性还给代码

Skill 可以打包可执行代码。这解决两件事：效率（让模型逐 token 生成排序结果，远不如直接跑一个排序算法）与确定性（同样的输入必须得到同样的输出，代码能保证，生成不能）。而且脚本代码不进上下文，只有运行结果回传。

具体应用场景

案例：PDF 表单填写 Skill

Claude 本身很懂 PDF 的「理解」，却不擅长「操作」——比如填写一份可交互表单。PDF Skill 就补上了这块能力。

  1. 1
    启动：上下文里只有核心系统提示 + 所有 Skill 的元数据（含 PDF Skill 的 name/description）+ 用户消息「帮我填好这份 PDF 申请表」。
  2. 2
    触发：模型从元数据判断 PDF Skill 相关，用 Bash 工具读取 pdf/SKILL.md，正文进入上下文（L2）。
  3. 3
    深入：SKILL.md 提到填表细节在 forms.md，模型判断确需填表，再去读它（L3）。提取字段则直接跑脚本，只拿回字段列表。
  4. 4
    执行：带着加载好的指令完成任务。关键：reference.md 等无关文件始终没进上下文，零 token 消耗。

4

易混淆问题与使用边界

▶ Skill 和普通提示词（Prompt）有什么区别？
提示词是会话级的、一次性的——换个对话就没了，你得重复粘贴。Skill 是文件系统级的、持久可复用的，模型会按需自动加载，你不必每次重申。更重要的是，只有 Skill 能带来渐进式披露与脚本执行：常驻成本约 100 token，而提示词要么全在上下文里、要么不在。
▶ Skill 和 MCP 是什么关系？会互相替代吗？
不会替代，二者互补。MCP 解决「连接」——让 Agent 能访问外部工具与数据源（数据库、Slack、Notion）；Skill 解决「知道怎么干」——封装流程知识、最佳实践、组织规范。一个竞争分析 Skill 完全可以指挥模型去调用网页搜索、经 MCP 访问内部数据库、再翻 Slack 历史记录，最后汇总成报告。
一句话：MCP 给的是手能伸多远，Skill 给的是活该怎么干。
▶ Skill 和 Subagent（子智能体）是一回事吗？
不是。Skill 是知识资产（一个文件夹），被加载进当前上下文指导行为；Subagent 是执行结构（一个独立运行的模型实例），拥有自己隔离的上下文窗口，只把结论回传给主 Agent。二者常配合使用：给子智能体配上专门的 Skill，让它在隔离环境里干活。
▶ 局限性：什么情况下 Skill 会失效或有风险？
  • 写不好 name/description 就不会被触发。模型完全依赖这两段元数据判断相关性。描述太模糊 → 该用不用；描述太宽泛 → 不该用乱用。这是最常见的失效原因。
  • SKILL.md 过重会浪费上下文。正文一旦超量，就该拆分到附属文件、保持主干精简。
  • 安全风险。Skill 可包含指令与可执行代码，恶意 Skill 可能引入漏洞或诱导数据外泄。只从可信来源安装；来源不明时务必审计其脚本与依赖，警惕要求连接外部不可信网络的指令。
  • 不是万能替代。模型本身不具备的基础能力（如极专业的领域推理），Skill 只能补充流程与知识，无法凭空创造能力；这类需求仍要靠模型能力或专门的模型/微调。
5

自测问题

Q1 你写了一个 Skill，内容正确详尽，但 Agent 从来不触发它。最可能的原因是什么？该怎么改？
参考答案：最可能是 frontmatter 的 name / description 没写好。模型在 L1 只能看到这两段元数据，它据此判断「当前任务是否需要这个技能」。正文写得再好，如果描述没能让模型对上号，就永远不会被读到（L2 不会触发）。
改进方向：
  • description 里写清做什么 + 什么时候用，包含用户可能说出的关键词和典型场景；
  • 避免过宽（什么都像相关）或过窄（几乎匹配不上）；
  • 站在模型视角检查：「看到这句话，我能否判断该不该用？」
Q2 一个 Skill 目录里塞了 50 个参考文件（总计 20 万 token），用起来会不会把上下文撑爆？为什么？
参考答案：不会，这正是渐进式披露的价值。未被引用的文件只是静静躺在文件系统上，消耗 0 token；只有被模型主动读取的文件才会进入上下文。可执行脚本甚至更极端——代码不进上下文，只有运行结果回传。因此一个 Skill 可捆绑的内容量实际上没有上限。
但有两个前提要注意：
  • SKILL.md 正文（L2）应保持精简，建议控制在 5k token 以内，并作为「目录」清晰地指向各个附属文件；
  • 互斥或极少同时使用的指引要路径分离，避免一次触发就拖入一堆无关内容。
